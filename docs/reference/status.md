# Language and compiler status

The primary language specification on this site follows the author's handwritten Combat example and corrected language handbook. Named initializers use `Field = value` without a leading dot; object access still uses `object.Field`. The table below records the implemented and tested contracts. Remaining native, proposed and host-specific examples are marked separately; platform, sanitizer and distribution validation are still required before a release is considered complete.

Source blocks marked `clp target` define specification examples. The marker is not displayed as an automatic warning on each example. These blocks remain excluded from executable example tests until their complete behavior is verified; they are never counted as passing compiler tests.

## Target syntax and current implementation

Protected colon calls, destructuring declarations and optional missing-key lookup
were explicitly deferred by the author. They are [future proposals](future-proposals.md),
not missing features of the current language release.

## What is available now

The current checkout provides a C++20 compiler, verified bytecode, a VM, an editor extension, and built-in math, window, graphics, UI, audio, files, JSON, and related modules. Individual APIs and runnable overlapping examples are documented in the library chapters.

The compiler rejects `struct`, named `func Name(...)` declarations, callback bodies without an explicit result after `->`, and shorthand `x => expression` lambdas. `func` introduces a typed anonymous callback. Named functions require explicit parameter types. Data values use `Type { Field = value }`; constructor calls and `new` are rejected. Only `enum class` with `Type::Case` is accepted. Aliases and unions use `def`; legacy `variant`, built-in `Option`/`Result` wrappers and intrinsic `Some`/`None`/`Ok`/`Err` constructors are removed. Modules use `link`, without `namespace`, `import`, `from` or `using` alternatives. Ignored `static` modifiers and `[[attributes]]`, `cout`/`endl`, `@field`/`@this::field`, untyped signals, direct signal calls and match arms using `~>` are rejected. Events use typed `signal<...>`, `::Fire` and `~>Connect`; match arms use `=>`. Task annotations retain a result parameter, and observables spell an explicit type or `auto`. Removed keywords remain reserved only to diagnose obsolete syntax and are excluded from editor completion. Ordinary user declarations named Some, Ok or Result have no intrinsic wrapper behavior.

## Diagnostics are a contract to implement

The Pacman and Combat references include expected failures, recovery behavior, and proposed diagnostic codes. They specify what future compiler work must test. No new diagnostic code is guaranteed merely because it appeared in an example. See [Errors and diagnostics](../guide/11-errors.md) for error categories, positions, and pending behaviors.

## Using a release

Read a release's own notes before assuming that it implements this target specification. Installing the existing VSIX does not add pending syntax. Small executable examples without a target notice demonstrate overlap with the current implementation; complete target projects need the compiler update.

## VM and transpiler use cases

The CL++ VM is the only official execution target. The author's Luau examples describe a use case: implementing a transpiler in CL++ that generates Luau for Roblox. Luau is not an official compiler backend, and Roblox-specific services and policies do not automatically become core language features.

The handbook separates these example host contracts from the language itself. Rust/Pest build instructions from earlier material do not apply to the current C++20 checkout.
